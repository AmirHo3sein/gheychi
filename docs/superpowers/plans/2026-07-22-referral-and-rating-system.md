# Referral & Rating System — Execution Record

**Date:** 2026-07-22
**Spec:** `docs/superpowers/specs/2026-07-21-referral-and-rating-system-design.md` (synthesized from a three-design judge panel — minimal-extend, event-driven, risk-first — with product decisions recorded and, where implementation surfaced real gaps, an "Implementation Addenda" section added after rollout)
**Status:** Complete — all 6 core slices shipped, back-to-back, each independently adversarially verified before the next began.

## What shipped

Six independently-shippable slices, each built as its own backend → frontend → adversarial-verify pass:

1. **Worker roster + worker ratings + editable reviews** — `workers` (salon staff, backed by a real `User` row via `findOrCreateByPhone`), `bookings.worker_id`, `worker_ratings` (submitted atomically alongside the existing salon `Review` through `POST /api/reviews`, one worker rating per review), new `PATCH`/`DELETE /api/reviews/:id` (72h edit window, `platform_config.review_edit_window_hours`). Provider-panel Team screen (add/deactivate staff, assign a worker to a booking), admin Worker Ratings moderation screen, public `GET /salons/:slug/workers[+ratings]`.
2. **Wallet ledger** — `wallet_balances` (read-optimized cache) + `wallet_transactions` (append-only, signed amounts), `WalletService.credit()/debit()` row-locked and never-negative (a debit is capped at the available balance, shortfall reported not thrown). Admin-only manual adjustment (`POST /admin/wallet/adjust`, mandatory audited reason) is the only producer in this slice. Customer `/account/wallet` balance + history page, admin Wallet Ledger screen.
3. **Referral codes + tracking** — one lifetime referral code per person (not per-role — a deliberate simplification over the design's original per-role-code proposal), `referral_reward_types` (3 rows, seeded `enabled=false`), `referrals` tracking rows. `referral_type` is resolved dynamically at redemption time from the referrer's current role (worker → salon_owner → user precedence), then frozen forever on the row. `POST /api/auth/verify-otp` extended with an optional `referralCode` that can never fail registration. Admin Referral Settings (per-type reward config) + Referrals (list/filter/cancel) screens.
4. **Reward granting (wallet-kind) + reversal** — `referral_rewards` (`UNIQUE(referral_id, beneficiary_role)`, the exactly-once backstop), `tryGrantReward` wired to booking-completion (inline) and payment-paid (hourly `ReferralGrantJob` sweep, honoring the `grant_holdback_hours` buffer), `reverseIfNeeded` wired to the refund-confirmation path. Introduced the `partially_granted` referral status (not in the original spec — see the design doc's Implementation Addenda) to honestly represent "one side granted, the other side's kind not yet supported" during the slice-4→6 rollout window.
5. **Discount-kind (`percent_discount`) rewards** — issued as literal, single-recipient rows in the *existing* `coupons` table (`coupons.issued_to_user_id`), reusing `resolveAndValidate`/`coupon_redemptions`/the no-stacking rule verbatim rather than a parallel mechanism. Also closed two gaps flagged by earlier slices' verify passes: R10 (`max_referrals_per_referrer`) enforcement, and admin visibility into reward terms/per-side grant status (`GET /admin/referrals/:id/rewards`).
6. **`fixed_discount` rewards** — `coupons.discount_fixed_amount` (mutually exclusive with `discount_percent` via a DB CHECK), `resolveBestPrice` extension to `discount.util.ts` (compares actual resulting prices, not raw percentages, so a fixed-toman coupon can correctly beat or lose to a percent discount). Isolated into its own slice specifically because it's the one piece touching tested, working, money-critical discount-resolution code from the earlier coupon feature — shipped with zero regressions to that suite.

## Verification

Every slice ran its own backend → parallel-frontend → adversarial-verify pipeline (26 agents total across 6 workflow runs). The verify pass in each slice was explicitly instructed to prove claims live against a real Postgres instance (concurrent-transaction races via parallel `psql`/`Promise.all` calls, direct SQL cross-checks, forced adversarial inputs) rather than trust the implementing agent's own report. Two real bugs were caught and fixed this way, both money-adjacent:

1. **Slice 5 — R10 race condition.** `max_referrals_per_referrer` was enforced via an unlocked count-then-insert; an 8-way concurrent redemption against a cap of 2 let all 8 through. Fixed with `SELECT ... FOR UPDATE` on the `referral_codes` row before counting; re-proven with the same adversarial probe (exactly 2 succeed), kept as a permanent regression test.
2. **Slice 2 — whitespace-only admin wallet-adjustment reason.** `@IsNotEmpty()` alone let a `"   "` reason through class-validator, defeating the "mandatory reason" requirement for a real money-moving admin action. Fixed with a `@Transform` trim before validation.

Final state: **1,312 tests passing** across all four apps (525 API unit, 413 API e2e, 66 provider-panel, 146 admin-panel, 162 user-app), zero regressions in the pre-existing coupon feature (independently re-verified after slices 5 and 6 specifically, since those are the two slices that touch it), all 6 migrations applied cleanly on both the dev and test databases with forward/reverse cycles proven.

## Notes for future work

Recorded as deliberate, explicit product decisions (not oversights) in the spec's "Product decisions" and "Suggested Improvements" sections: no worker SMS invite flow yet (`findOrCreateByPhone`-on-add is the only mechanism for now), wallet balance is accrue-only (no spend-at-checkout integration), no referral campaigns/tiers/multi-level referrals, no IP/device fraud-signal capture, no automated leak-report for the one accepted non-reversible case (an already-redeemed discount reward surviving its qualifying booking's refund). Reward amounts ship as placeholders (`enabled=false`, zero-value terms) — real toman/percent/point values are an admin data-entry task via the shipped Referral Settings screen, not a code change.
